# Durable recording: design and operations

Status: Phase 0.3 architecture implemented on this branch. Owner: Shan.

A recording is a pipeline with five responsibilities that used to be tangled
into one closure. This change separates them so that **audio captured by the
microphone is never lost to a refresh, a closed tab, a network drop, an
expired sign-in or a crash** — and so that no work (upload, transcription) is
ever done twice or lost:

1. **Capture** — the microphone and the encoder. Local only. A dropped
   network or a signed-out state never stops a recording.
2. **Durable journal** — IndexedDB. Every ~1 s of captured audio is
   committed to disk *before it is counted*; a part is rebuilt only from
   committed slices.
3. **Live display** — the on-screen transcript. A view, never the source of
   truth.
4. **Durable processing queue** — IndexedDB rows (browser) and SQLite rows
   (backend). Jobs survive refresh/restart; a job is claimed by exactly one
   transaction; retries are bounded by backoff and never silent.
5. **Cloud workspace copy** — Firebase. A copy for multi-device visibility,
   not the recording engine. Local capture does not depend on it.

## 2. Data flow

### 2.1 Capture → journal

`MediaRecorder` runs with a 1 s timeslice (`recorder.start(1000)`). Each
`dataavailable` blob is (a) appended to the part's in-memory chunk list, as
before — the part blob on stop is the concatenation of exactly these chunks,
so the part audio is byte-identical to the pre-change stream — and (b)
committed to the journal's `slices` store under
`${noteId}:${slot}:${seq padded to 8 digits}`. The commit resolves only on a
committed IndexedDB transaction (the "commit ack"); a failed commit is
logged and the slice stays in memory only — it degrades recovery
granularity, it never stops the recording.

Slices use a **per-part seq starting at 0**: each part has its own recorder,
and a MediaRecorder's first timeslice carries the EBML header +
Info/Tracks, so a part's slice stream from seq 0 is a self-contained valid
WebM. That is what makes slice-only rebuild possible.

When a part completes, its whole blob is written to the v1 `parts` row
(exactly as before), and the part's slices are then dropped — verified
first by re-reading the row and matching the blob size. Completed parts
keep their audio in the part row; slices exist to recover parts that never
completed.

### 2.2 Recovery (refresh / closed tab / crash)

On load, `recRecoverInterrupted()` runs before the existing v1 restore:

- a session row whose `capture` is still `recording` was interrupted;
- for each slot with committed slices and no part-row blob, the slices are
  concatenated and run through `NzRecRecovery.recover`:
  **strict** first (cut before the first incomplete element — always safe),
  **salvage** second (a truncated final Cluster is kept with its size
  rewritten to the 8-byte unknown-size VarInt and cut after its last
  complete child — an unknown-size Cluster terminates at EOF by spec).
  Recovery walks the EBML element tree by (id, size-varint) pairs, never by
  signature search, and the output is always a byte prefix of the input:
  every complete second that made it to disk is kept, only the incomplete
  final region is discarded, and nothing is invented. The result is written
  back as an ordinary held part (status "needs retry" in the UI).
- a part whose slices do not produce a structurally valid file (e.g. the
  crash happened before the first slice committed) stays lost and is logged —
  never guessed at.

The existing v1 restore then reopens the note with the held parts, the
existing 30 s flush sends them, and each held part additionally gets a
durable `rec-transcribe` job.

### 2.3 The durable queue (browser)

`NzRecJobs` (Web Lock `"notez-rec-jobs"` so exactly one tab runs the loop):

- jobs are rows in the journal's `jobs` store:
  `{jobId, dedupKey, type, ref, state, attempts, nextAttemptAt, lease, uid,
  payload, error, result, createdAt, updatedAt}`;
- states: `queued → running → done`; failures re-queue with backoff
  `min(30 min, 30 s · 2^attempts)` — a job is never dropped silently;
- a claim is a state change with a **90 s lease**; only an *expired* lease is
  recovered (a live lease is never stolen, so a crashed worker delays a job
  by at most one lease);
- **idempotency by dedupKey**: `up:{noteId}:{slot}` for uploads,
  `tr:{noteId}:{slot}` for transcriptions. Enqueueing the same logical work
  twice returns the existing job.
- **auth-aware (R1)**: `window.nzRecAuthLost()` (wired into every sign-out
  path and the SDK token-expiry event) parks every non-done job in
  `awaiting-auth`; the parked jobs re-queue automatically when a signed-in
  uid is back. Jobs carry the uid they were created for and are never
  claimed by a different uid (an account switch cannot process another
  account's work). The audio and session rows are untouched by a sign-out.
- signed-in sessions only: a guest's held parts keep the existing
  protection (v1 journal rows + the 30 s live re-flush); a guest is never
  claimed backed up.

Handlers (registered by 06):

- `rec-transcribe` re-runs the held part through the ordinary send pipeline
  (`recSendPart`). A part that is already sent, whose note is gone, is a
  terminal skip; a session that is not open on this tab defers (30 s, no
  attempt spent) until the restore reopens it.
- `rec-audio` rebuilds the part from the journal (part row, else slices) and
  uploads it via `NzRecCloud.putPartAudio`. It reads audio from disk, never
  from memory, so it works whether or not the session is open.

### 2.4 The durable queue (backend)

`backend/app/jobs.py` — a SQLite file (`data_dir/notez-jobs.sqlite3`, beside
the existing `notez-indexing-queue.sqlite3`):

- `job_key` is **UNIQUE**: `transcribe:{noteId}:{partSlot}:{model}`. A
  browser retrying the same part with the same model gets the existing job
  back (done → instant result, running → poll, failed → explicit `/retry`),
  so a duplicate transcription is impossible. The model is in the key so the
  client's model walk is not blocked by a job that failed on an earlier
  model of that walk.
- `claim_next()` is one `BEGIN IMMEDIATE` transaction: select the oldest
  due job, mark it running with a 300 s lease, increment attempts. The
  SQLite single-writer guarantees one claimer.
- `fail()` re-queues with backoff under 5 attempts; at the limit the job is
  terminally `failed` — only `POST …/retry` re-queues it.
- `recover()` (at startup and every worker loop) puts lease-expired running
  jobs back to queued; a live lease is never stolen.
- `purge()` drops done/failed jobs older than 7 days.
- the connection is autocommit (`isolation_level=None`) + `busy_timeout`
  with explicit `BEGIN IMMEDIATE` steps — the P0.3a backend-job prototype
  (6/6, real SIGKILL) showed the legacy implicit-transaction mode silently
  swallows "cannot start a transaction within a transaction".

The worker (a task started in the FastAPI lifespan) claims one job at a
time and transcribes it with the same Gemini model walk the inline
`/v1/ai/generate` path uses (requested model first, then the configured
transcribe chain on 404/429/503).

### 2.5 The cloud workspace copy

- **Gate.** `GET /v1/firebase-config` (existing, unauthenticated endpoint)
  gains `storageEnabled`. Default **false**: recording audio uses the
  Realtime Database chunk layout (the app's existing attachment convention:
  510 KB base64 chunks, 4 in parallel, **meta written last** so a
  half-finished upload is never a complete file). Storage is used for audio
  only when the deployment says it is configured — enabling it is an
  operator action (see §6), and no Firebase project, bucket, rules, IAM or
  billing change is made by this code.
- **Claim (one capture per user+note).** `users/{uid}/rec/{noteId}/claim`
  via an atomic `runTransaction` with a 30 s expiry, a 10 s heartbeat while
  owned, and an `onDisconnect` release, so a crashed tab lets go of the
  claim on its own. A conflict **never overwrites**: the losing device keeps
  recording locally, shows a notice, records `cloudClaimed: 0` on its session
  row, and its parts get **no** cloud-upload job for the lifetime of that
  session — its audio stays on its own device rather than being written into
  the other device's live part numbering. `putPartAudio` additionally
  refuses (the job retries) while a claim is *currently* held by another
  device, so even a session that held the claim cannot upload into a
  concurrent capture.
- **Audio.** One stable key per part:
  `users/{uid}/rec/{noteId}/audio/{slot}` (RTDB chunks + `meta`) or
  `users/{uid}/rec/{noteId}/audio/p{slot}.webm|wav` (Storage object).
  The `meta` carries the part's **sha256**; a matching meta means
  "already uploaded", so a retry never re-uploads, and a replaced copy
  (a part recovered with different bytes) overwrites the same stable key —
  a part is never written twice under two keys. `audioIndex/{slot}` is the
  per-part manifest for multi-device listing; `getPartAudio` reads a part
  back for other devices.
- **Session.** `users/{uid}/rec/{noteId}/session` (read-modify-write beside
  the claim, which it never clobbers).
- **Deletion.** Explicit only. `discardSession()` (wired to the confirmed
  Discard button) removes Storage objects, then the whole
  `rec/{noteId}` subtree, and writes the tombstone
  `users/{uid}/rec-tombs/{noteId}` **last**. All cloud writes first check
  the tombstone and refuse (loudly logged) when it is present, so no device
  can resurrect a discarded session.
- **Honesty.** Every operation resolves to a `mode`:
  `local-only` (guest / offline / no config), `rtdb`, `storage`,
  `tombstoned` or `failed`. The local journal and the live pipeline never
  depend on any of it.

### 2.6 Transcripts: machine text vs user edits

Two surfaces (the `## Transcript` section in the recording note, and the
dedicated `{id}-tx` transcript note) share one commit rule:

- while the stored section equals what the machine last wrote, the machine
  rewrites it in full on every save (how new parts appear, exactly as
  before);
- the moment the stored text differs, the section becomes **user-owned**:
  its existing lines are never touched again — not even by speaker renames —
  and newly finished parts are appended below, each block marked
  `<!-- rec: machine-appended part -->`, so machine text and user text are
  distinguishable in the stored note;
- partial vs final stays explicit in the note header ("Recording in
  progress" vs "Recording finished");
- after a reload, a stored transcript that already differs from the
  machine's rebuilt text is treated as user-edited (conservative: the user
  wins by default across a reload);
- per-segment state (pending / in progress / done / held) lives in the
  per-part state machine and the journal rows, not in the note body, so the
  existing note format and its readers (`recSavedParts`, history UI) are
  unchanged.

### 2.7 Pre-transcription voice enhancement (client-side, additive)

A completed part is passed through `NzRecEnhance.enhanceForTranscription`
(`app/17-rec-enhance.js`) at the top of `recTranscribePart` — the single
point where the part's audio bytes are assembled for the provider (both the
direct-own route and the managed route, including the durable job-create
request). The chain is browser-native (no new dependencies, no local
AI/GPU):

```
decode (AudioContext, requested 48 kHz — the recorder's native Opus rate)
  → measure peak + RMS
  → adaptive loudness normalization
  → gentle 80 Hz high-pass (rumble; no noise gate, no denoising)
  → conservative limiter (no clipping)
  → encode lossless mono 16-bit PCM WAV
  → submit the ENHANCED audio to the provider
```

The derivative is **mono** (stereo is downmixed to a faithful average; the
provider does not use channel position) and is rendered at the **actual
decoded sample rate** (48 kHz in the target browsers — no unnecessary
resampling) as **lossless 16-bit PCM** (no lossy re-encode).

Loudness is **adaptive, not a fixed multiplier**: quiet parts are raised
toward a −18 dBFS RMS target (gain capped at +18 dB so background noise is
not amplified into the signal), loud parts are lowered (floored at −6 dB),
parts already near the target are left within a ±0.5 dB dead band, and
near-silence below −55 dB is left at unity (never amplified). The high-pass
is gentle (80 Hz, Q 0.7) so it removes electrical/handling rumble without
eating the low-frequency energy that carries much of the intelligibility of
Urdu, English, Roman Urdu, Punjabi and Arabic; there is deliberately **no
noise gate and no spectral denoising**, so quiet syllables and soft
consonants survive.

Guarantees (Phase 0.3 corrections, in force):

- **The original part is never modified, overwritten, or replaced.** It stays
  byte-identical in the durable journal and the cloud copy. Only the
  transcription request's payload is swapped, and only on success.
- **Voice samples are NOT enhanced** — they are identity references and must
  stay untouched.
- **The derivative is never persisted** anywhere. It is built fresh on every
  call, so a retry always enhances the pristine original, never an
  already-enhanced file (idempotent by construction). No duplicate permanent
  audio files are created.
- **Any failure falls back to the original blob** (unsupported browser,
  decode/render error, or an oversized enhanced payload) with
  `meta.succeeded=false` + a reason. Enhancement can never block or lose a
  transcription.
- **Nothing is ever truncated.** A part is either fully enhanced and fits, or
  sent as the original — never a shortened version of either.
- **The payload-size guard is verified** against the managed route's actual
  request body (the 8,000,000-byte backend cap): the enhanced WAV is capped
  at 4,000,000 bytes (44-byte header included), leaving margin for the
  voice samples (≤ 1,200,000 b64 chars, hard-capped and never truncated),
  the prompt, the system prompt and JSON structure. The default 40 s part
  (3,840,044 bytes) still fits; longer parts (no-limits mode) are sent as the
  original Opus, which is tiny and always fits. The direct-own route's
  looser cap is not the binding constraint.
- **Out-of-range 16-bit samples are impossible** by construction
  (`floatToI16` clamps to [−1, 1]); the gain stage also holds the loudest
  sample at/below the limiter threshold before the high-pass, with the
  limiter and the clamp as backstops against transient overshoot.

Observability is diagnostics-only: one meta object per part (original and
enhanced RMS/peak, applied gain dB, success/fallback + reason, duration,
output format + byte size, decoded channel count) is stored on
`REC.enhance[index]` and logged via `console.debug`. It is intentionally
**not** surfaced in the normal recording UI.

Configuration: on by default; per-user switch `notez-ai-enhance`
(`aiStore`, `'0'` disables without a reload); every parameter is overridable
via `NzRecEnhance.configure({...})`. No provider, model, prompt, chunk
duration, Firebase, auth or backend change.

## 3. Schema changes

### 3.1 IndexedDB `notez-rec-journal` (v1 → v2)

Same database, same v1 `parts` store, untouched rows. The upgrade adds
three stores (new devices get all four):

| store | key | row |
|---|---|---|
| `parts` (v1, unchanged) | `key` = `${noteId}:${index}` | `{noteId, index, blob, text, wall, mark, status}` — the blob is now **merged, never nulled**: once journaled it stays |
| `slices` | `key` = `${noteId}:${slot}:${seq}` (seq padded to 8 digits, so key order = seq order) | `{noteId, slot, seq, mime, at, blob}` — ~1 s committed capture slices; dropped once the part row holds the whole part |
| `sessions` | `noteId` | `{uid (fixed at session open, never rebound), mode, mime, startedAt, capture: recording/stopped/recovered/discarded/awaiting-auth, finalizedAt, deletedAt, notesCursor, cloudClaimed: 0/1 (this device holds/lost the claim at session open), updatedAt}` |
| `jobs` | `jobId` | see §2.3 |

### 3.2 Realtime Database (all under the user's existing namespace)

```
users/{uid}/rec/{noteId}/claim         {uid, tab, claimedAt, expiresAt}
users/{uid}/rec/{noteId}/session       {uid, mode, mime, startedAt, capture, finalizedAt, updatedAt}
users/{uid}/rec/{noteId}/audio/{slot}/c/{i}   base64 chunks (RTDB layout)
users/{uid}/rec/{noteId}/audio/{slot}/meta    {sha, mime, size, chunks, at, backend} — last
users/{uid}/rec/{noteId}/audioIndex/{slot}    {sha, mime, size, at, backend}
users/{uid}/rec-tombs/{noteId}        {at, uid}                                — written last on discard
```

Storage layout (only when `storageEnabled`): the object
`users/{uid}/rec/{noteId}/audio/p{slot}.{webm|wav}` replaces the
`audio/{slot}/c/*` chunks; `meta`/`audioIndex` stay in RTDB either way.

### 3.3 SQLite `data_dir/notez-jobs.sqlite3` (new file)

```
ai_jobs(job_id PK, job_key UNIQUE, uid, type, status, attempts,
        next_attempt, lease_owner, lease_until, payload_json, result_json,
        error, created_at, updated_at)
```

## 4. API changes

All additive; existing endpoints are unchanged.

| endpoint | change |
|---|---|
| `POST /v1/ai/transcribe` | new. Body: `note_id, part_slot, prompt, system_prompt?, temperature?, model?, images[] (audio first), audio_transcription?`. Creates the durable job idempotently and returns `{jobId, created, status, attempts}`. Authenticated; BYOK keys are intentionally **not** accepted (a durable row should not hold a user's own key — own-key parts stay inline). |
| `GET /v1/ai/transcribe/{jobId}` | new. Poll. `{status: queued/running/done/failed, attempts, text?, model?, error?}`. Owns the lighter 120/min limiter so polling a long transcription never trips the general 30/min limit. |

| `GET /v1/firebase-config` | `storageEnabled: bool` added (default `false`). |

## 5. Backward compatibility

- Existing recordings: v1 journal rows are untouched and still restore
  exactly as before (the v1 restore path is unchanged; the new recovery
  only *adds* rebuilt parts to it). Notes saved by older builds parse with
  the same readers; the transcript section format is unchanged.
- The v1→v2 database upgrade never touches existing rows; an old tab that
  still holds a v1 open is handled by IDB's normal version negotiation
  (`onblocked` is tolerated).
- The 1 s timeslice changes no part's bytes: the part blob is the
  concatenation of the same stream (verified in the P0.3a harness design;
  not re-measured in this sandbox — see §7).
- The frontend's managed transcription route now prefers the durable job;
  a backend without the new endpoint simply 404s the POST, the error is
  caught, and the part goes held exactly as before — but the inline route
  is tried only for own keys, so a very old backend + signed-in user degrades
  to held parts rather than silently re-running inline. (This branch ships
  the frontend and backend together.)
- `sw.js` is regenerated; the cache name changes, so a one-time re-download
  of the shell on update, as with any release.

## 6. Configuration

No new required configuration. Optional:

- `FIREBASE_STORAGE_ENABLED=true` (backend env) — the operator's answer to
  "is Firebase Storage configured for recording audio?". To actually turn
  it on you must first, **in the Firebase console (separate approval, not
  part of this change)**: create/keep the Storage bucket for the project,
  and add security rules allowing the signed-in user to read/write/delete
  under `users/{uid}/rec/**` only. Until both are done, keep the flag
  false — the RTDB layout works without any of it. The flag is served to
  the frontend via `/v1/firebase-config`; the frontend never calls Storage
  when it is false.
- `NOTEZ_DATA_DIR` (existing) — the jobs SQLite lives there.
- `notez-ai-enhance` (browser `aiStore`, default `'1'`) — the per-user
  on/off switch for pre-transcription enhancement (§2.7). Setting it to
  `'0'` sends every part as the original Opus without a reload. All DSP
  parameters (target loudness, gain bounds, high-pass, limiter, size cap)
  are module defaults in `app/17-rec-enhance.js`, overridable per-call or
  via `NzRecEnhance.configure({...})`; they are intentionally not exposed in
  the recording UI.

No credentials, API keys, bucket names or environment-specific values are
hardcoded anywhere; everything comes from the existing settings.

## 7. Known limitations and decisions needing attention

1. **First ~1 s of a part.** If the process dies before the first slice of a
   part commits, that part has no EBML header on disk and cannot be rebuilt
   (a headerless WebM is not a file). The loss is bounded by one timeslice
   and is logged; nothing is invented to fill it.
2. **Reload and user-edited transcripts.** A stored transcript that differs
   from the machine's rebuilt text after a reload is treated as
   user-owned, and the machine then only appends *new* parts. Speaker
   renames made before the reload are not re-applied to a user-owned
   section (the user's text wins, by design).
3. **BYOK durability.** A browser with its own Gemini key transcribes
   inline (the key does not go into a durable job row). A BYOK part whose
   send outlives the tab is recovered through the v1 journal + the live
   flush on the next load, plus a durable queue job when the user is signed
   in.
4. **Cloud copy size.** Audio is retained permanently, locally and (for
   signed-in sessions) in the cloud copy. At the current 32 kb/s Opus
   setting, one minute of recording is roughly 230 KB of WebM (≈ 310 KB as
   RTDB base64). A one-hour class is on the order of 14 MB locally and
   ~19 MB in RTDB. If this is too much for the Firebase plan, set
   `FIREBASE_STORAGE_ENABLED=true` after configuring Storage (Storage
   pricing is cheaper per GB than RTDB), or re-visit the retention policy —
   both are product decisions, not code changes.
5. **Claim granularity.** One capture per (user, note). A second device
   opening the same note sees the conflict notice and records locally; its
   session keeps its audio on-device (no cloud upload for that session), so
   no device's part numbering is ever overwritten. If the first device lets
   go (stop, crash, tab close), the second device's *next* session acquires
   the claim normally and uploads its audio.
6. **Recovery = structural, not audited.** `recover()`/`structuralCheck`
   verify EBML structure (headers, Info, Tracks, complete Clusters). They
   do not decode the opus payload; a structurally valid file is claimed
   valid as structure, and that is the guarantee the code makes.
7. **The Live API (streaming transcription, P6) and the cost model (P7) are
   out of this authorization** — no new services, no new spend.

## 8. What is not verified here

This change was checked at the code level only (`node --check` on every
touched script, `python3 -m py_compile` on the backend, the repo's own
`scripts/generate.mjs --check`), per the Phase 0.3 working agreement — no
browser was run in this environment. The building blocks carry their own
verification from P0.3a: the EBML recovery logic (114/114 cases), the WAV
reconstruction (8/8), the IndexedDB commit-ack contract (6/6), and the
SQLite jobs pattern (6/6 including a real SIGKILL). The browser-side
behaviours that still need a real run on the author's machine: a
refresh/crash mid-part (T1–T4 of the P0.3a harness), a sign-out mid-send, a
claim conflict between two devices, and the RTDB upload of a long session.

The enhancement pipeline (§2.7) is additionally unverified at runtime: the
measured loudness behaviour of the gain/high-pass/limiter chain, the
clip-free result after 16-bit conversion, and the provider's acceptance of
`audio/wav` on the pinned transcribe models are all code-level analysis
only. **No claim is made that transcription accuracy has improved** — that
requires real before/after audio comparisons, which have not been run.
